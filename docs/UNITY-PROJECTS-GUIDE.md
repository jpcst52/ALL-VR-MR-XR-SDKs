# The Unity projects explained (plain language)

Written 2026-11-08 for the owner. General safety-awareness practice only. Everything that was run was run in SteamVR's simulated headset (which has no controllers) or in the editor; the last section says what is verified.

## 1. The short version

- There are **four small scenario projects** (01 to 04) and **one big project called the hub**. Each is a separate Unity project with its own folder, its own scenes and its own `ProjectSettings`. You open one at a time in Unity.
- The **hub** is not "the scenes of the other four". It is one Unity project that holds a **Lobby** scene plus its **own copy of each of the four scenarios** (saved as `HydrostaticTest_Hub`, `RefineryRounds_Hub`, `WarehouseForklift_Hub`, `ResistorBench_Hub`). That way one program (one `.exe`) can start in the Lobby, walk through a doorway, and switch to a scenario, and come back.
- All five projects use **one shared kit**, the folder `vive-steamvr/packages/com.pittbradford.xrtraining`. Fix the kit once and every project gets it. The kit holds the headset/hand code, the pointing ray, the grabbing, the text boards, and the first scenario (Hydrostatic Test Bay) itself.
- Every scene (the Lobby, the four hub scenarios, and the four standalone scenes) now has **the same player rig, hands, hint panel and pointing ray**, saved as real objects in the scene file. An audit tool proves it (section 6).

## 2. What each folder under `vive-steamvr` is

| Folder | What it is | Open it in Unity? |
|---|---|---|
| `01-hydrostatic-test` | Standalone project: the Hydrostatic Test Bay. Its scenario code is **in the kit** (`Runtime/Scenarios/HydroTest.cs`), so the project has almost no scripts of its own. | Yes, alone |
| `02-refinery-rounds` | Standalone project: Refinery Rounds. Scenario code in its own `Assets/Scripts`. | Yes, alone |
| `03-warehouse-forklift` | Standalone project: Warehouse and Forklift. Its own scripts, plus a seated Rocketbox driver that the hub copy does not have (section 5). | Yes, alone |
| `04-resistor-bench` | Standalone project: Resistor Bench. Own scripts. | Yes, alone |
| `hub` | The Lobby plus a copy of all four scenarios, so one build can switch between them. Needs licensed Asset Store packs and Rocketbox people that are **not in git** (`Assets/Scenes/Local`, packs), so it only builds on the lab PC. | Yes, alone |
| `packages/com.pittbradford.xrtraining` | **The shared kit.** Not a project. Every project lists it in `Packages/manifest.json` as `file:../../packages/...`. | No (edit it from any project) |
| `steamvr-sample` | Valve's own sample scene, built only to answer "does Valve's plugin work on this Vive?". Git-ignored, generated by `scripts\setup-steamvr-sample.cmd`. | Only for that test |
| `steamvr-setup` | Not a project: two helper editor scripts (`SteamVRProjectSetup.cs`, `SteamVRSampleSetup.cs`) that `scripts\setup-steamvr.ps1` copies into a project to move it onto Valve's SteamVR plugin (loader, Direct3D 11, actions). | No |

**Why "scenes in the hub, then separate projects"?** The four projects exist so something always works on its own if another breaks (and so each can be handed out alone, with only free assets). The hub exists so one `.exe` can show the whole thing. The hub copies are rebuilt from the same scripts but dressed with the licensed art, so they look richer.

## 3. How the Lobby loads a scenario

1. The hub build starts in the scene **Lobby** (first in Build Settings). `LobbyHub.cs` (in `hub/Assets/Scripts/Lobby`) owns it. There are four portals (doorways) with a pad on the floor in front of each.
2. **Three ways to choose** (as of this round; the second is new):
   - stand on a portal's pad for about 1.4 seconds (the pad shows "Starting 40%"), or
   - **point at the doorway and press the trigger** (desktop: left click). Pointing at it shows "Press the trigger" on the pad and the doorway grows a little, or
   - desktop only: press **1, 2, 3 or 4**.
3. `SceneManager.LoadScene("RefineryRounds_Hub")` (and so on) switches scenes. In each hub scenario a small object, `Return to lobby` (`ReturnToLobby.cs`), watches for **Backspace** or **both grips held for 1.5 s** and loads the Lobby again.
4. A scenario project on its own has no Lobby and no return; it is just that one scene.

## 4. What is in every scene's Hierarchy

The same objects in all nine scenes (checked by the audit, section 6):

```
XR Rig                              (empty object at the start position)
  Player (SteamVR)                  Valve's Player prefab
    SteamVRObjects
      VRCamera                      the head camera (tagged MainCamera)
        Desk Hint                   small blue panel with the keys; saved switched off, the backend
                                    switches it on only at the desk
      LeftHand, RightHand           Valve's tracked hands, each with a child
        LeftHand render model       "<Hand> render model": Valve's controller / glove model. It is
        RightHand render model      empty until Play; SteamVR supplies the mesh when it runs
      BodyCollider, Overlay, [SteamVR]
    NoSteamVRFallbackObjects        Valve's own 2D camera and hint text for a PC with no headset
      FallbackObjects, FallbackHand   (the kit now switches these off for that run, section 6)
    FollowHead, InputModule, PlayVolume, DebugUI, Snap Turn ...   other parts of Valve's prefab
Teleporting (SteamVR)               Valve's teleport arc and rules
PB Teleport Area                    one flat mesh where the trackpad arc may land (the floor)
```

- **The hand objects look empty in the Hierarchy and Scene view.** That is normal: Valve's `render model` objects fetch the controller mesh from SteamVR at Play. This is identical in the Lobby and in every scenario (the audit counts zero renderers on all of them in edit mode).
- Besides that: the boards (`Task Board`, `Footer`, `Why cue`), props, lights and so on are saved objects too. **No scene content is created from code at Play** (the repository rule); the kit's own desktop rig and `DeskSelfTest` are the exceptions listed in section 9.
- The Lobby has no Task Board or Footer (nothing to teach there) and, until this round, no object you could point at (no `Pressable`), which is why it behaved differently (section 7).

## 6. The consistency audit (what was checked, by evidence)

Tool: kit `Editor/SteamVR/SceneConsistencyAudit.cs`. From a command line, with the project closed:
`Unity.exe -projectPath P -executeMethod PittBradford.XR.EditorTools.SceneConsistencyAudit.RunAndExit -pbScenes "Assets/Scenes/X.unity" -pbAuditOut report.txt` (menu: **Pitt-Bradford > Audit scene consistency (open scene)**). It lists the rig, Teleporting, PB Teleport Area, Desk Hint, active cameras, missing scripts, and counts of Pressable / Grabbable / Task Boards / Footers. It only reads scenes.

Result for all nine scenes (Lobby, four hub scenarios, projects 01 to 04): **Player (SteamVR), VRCamera, both hands with render models, Desk Hint, Teleporting and PB Teleport Area are present and set the same way.** So the saved scenes were already consistent; the differences you saw came from how they behave, and from the Lobby having nothing to point at. Findings:

| Finding | Where | Status |
|---|---|---|
| **SteamVR pauses the game when the headset is in standby or the dashboard is open.** A Vive nobody is wearing, and SteamVR's simulated headset, go to standby about 5 s after the app starts (SteamVR's own log: "leaving standby", then "entering standby" 5 s later). Valve's code then sets `Time.timeScale` to 0, so walking, the Lobby pad timer and anything on game time **do nothing**. This is the most likely meaning of "the controllers do nothing" at the desk. I hit it myself: my desk tests stalled with the game frozen at `timeScale 0`. | all scenes, standalone and hub | **Fixed** in the kit (`SteamVRBackend` desk mode, see below) |
| In that same state SteamVR also makes each Valve hand "hold" a dummy object (`_application_lost_focus`), so the hands cannot hover or grab; and once the game runs again Valve's `Hand.FixedUpdate` throws a NullReferenceException every physics step (439 in 12 s in project 01, 13,000 in the hub). | all scenes | **Fixed**: desk mode claims input focus back through SteamVR's own focus event, which makes the hands let the dummy go |
| The Lobby had **no Pressable**: nothing could be pointed at and pressed (the desk self-test said "no Pressable in this scene"). Portals worked only by pad dwell or keys 1-4. | Lobby | **Fixed** (section 3): collider and Pressable on each portal's Gate, pointer reach 20 m, board text updated. Hub scripts are updated; the Lobby scene file needs one menu click (below) because your hub editor is open |
| With **no headset and SteamVR not running**, Valve's Player showed its own "WASD EQ/Arrow Keys to translate the camera" text and a second camera over the kit's rig, with the wrong keys. Same in every scene. | all | **Fixed** in the kit: with no headset the saved Valve Player and Teleporting are switched off for that run only |
| `HubPolish` threw a NullReferenceException every frame in the hub Warehouse (it tried to add a PostProcessLayer to a camera that already had one): 13,000 exceptions in a few seconds. | hub scenarios | **Fixed** in `hub/Assets/Scripts/Lobby/HubPolish.cs` |
| 18 and 26 **missing scripts** on Asset Store pack lights (`Construction Light Floor`, `StandingLight`) in `HydrostaticTest_Hub` and `RefineryRounds_Hub` | hub only | Not fixed, harmless to play; they come from the packs |
| Project 03 `Forklift.cs` differs from the hub copy (seated Rocketbox driver) | 03 vs hub | Known, deliberate; see section 5 |
| Hub has the Unity post-processing symbol (`UNITY_POST_PROCESSING_STACK_V2`) and a different quality-level list; 01-04 do not | hub | Left as is (the hub's polish uses post-processing) |

Project settings compared (01, 02, 03, 04 and hub): **identical** on Active Input Handling (`activeInputHandler` 2 = both), OpenVR loader assigned, Direct3D 11 only, OpenVR `StereoRenderingMode` 1 (the player log says "Single Pass Instanced"), mirror view mode 2, quality level 5, splash screen off, full-screen mode 1, window 1024 x 768, `PB_STEAMVR` define set, Unity 6000.3.20f1, and the same kit (referenced by path, version 0.1.0). MSAA comes from the shared quality level and the camera (`allowMSAA`). `steamvr-sample` is deliberately different (plugin defaults).

**To finish the Lobby in your hub editor** (the scripts are already in place; the scene file is git-ignored and your editor has the hub open, so I did not edit it): open `Assets/Scenes/Local/Lobby.unity`, run the menu **Pitt-Bradford > Hub: lobby portals selectable by pointing (open Lobby scene)**, then save the scene (Ctrl+S). It adds a collider and a Pressable to each of the four `Gate` objects and updates the board text. It is the same thing `LobbyHub.BuildPortal` now does when the lobby is rebuilt, and it is safe to run twice. Tested on a copy of the hub (section 11).

## 7. "The hub shows no controllers, but the Hydrostatic test does, and they do nothing"

What I could and could not reproduce:

- **Reproduced, same in both:** at the desk in the simulated headset, the Lobby and project 01 show the same Valve glove hands, the same keys panel and a thin pointer line (pictures in section 10). The kit rig, the settings and the saved objects are the same. So I could **not** find a Lobby-versus-01 difference in how the hands are drawn. If your editor really shows something different, tell me how you press Play (is SteamVR running? which scene? Game view clicked?).
- **Why the controllers "do nothing":** (1) the simulated headset has **no tracked controllers**, so the desk hand (keyboard and mouse) stands in: WASD walks, the mouse looks, **left click = trigger** on what the ray touches, **hold E = grab** (within 3 m). Valve's glove models are drawn in a fixed rest pose in front of you and never move, because nothing tracks them. A real wand model only follows your hand when a real wand is tracked. (2) The finding at the top of section 6: SteamVR **freezes the game** when the headset is in standby, and blocks the hands, so even the desk keys appeared dead. That is now overridden in desk mode (and given back as soon as a real controller is tracked).
- **Why the Lobby felt dead:** in the Lobby, click did nothing at all, because no portal could be pointed at. That is now fixed.
- **Why a no-headset editor run looked different:** with SteamVR **off**, the editor cannot start VR. The kit then builds its own blue controllers and Valve's fallback text appeared over it. That is cleaned up. In that mode: WASD walk, right mouse look, left click press, **T** hold and release teleport, E grab.

## 8. How to run each at the desk, and what changes with real wands

**With SteamVR running and the simulated headset (or a Vive with no controllers on):**

| Key | Does |
|---|---|
| W A S D | walk (limited to the training area) |
| Mouse | look (the first click locks the mouse; **Esc** frees it) |
| Left click | the trigger: presses the valve, button or portal the ray touches |
| Hold **E** | grab what the ray touches within 3 m; release E to let go |
| Backspace | (hub scenarios) back to the Lobby |
| 1 2 3 4 | (Lobby) go straight to a scenario |

**With real Vive wands:** point with the right wand and pull the trigger to press; grab by reaching the object and squeezing the grip; hold the trackpad, aim the arc at the floor area and release to teleport; both grips for 1.5 s returns to the Lobby. As soon as a wand is tracked the desk keys switch off by themselves and Valve's real hand models take over.

**Run a project in the editor:** open the project (Unity 6000.3.20f1) and press Play; start SteamVR first (it is what provides the simulated headset), then click once in the Game view so the keys work.
